### 모니터링 구축 및 보고서 자동화  `[운영/인프라 · 보조]`
MSP로 관리하는 40개 고객사의 클라우드 인프라 모니터링 체계가 없어, 장애 감지와 월간 운영 보고서를 수작업으로 처리하던 환경에서 모니터링 스택을 직접 제안하고 구축한 프로젝트입니다.

**기여도 (팩트)**: 제안부터 40개사 전체 구축·알람 연동까지 단독 수행.

KT Cloud Watch는 CPU/Memory/Disk/Network In·Out 기본 지표를 7일만 보존하고 알람은 메일로 왔습니다. 다만 7일이 지난 장애는 지표가 사라져 사후 원인 추적이 불가능했고, 40개 고객사를 한눈에 보는 통합 관제나 애플리케이션·커스텀 지표 수집이 없어 문제가 생기면 수십 개 서버를 일일이 접속해 로그를 뒤져야 했습니다. 월간 보고서도 서버마다 직접 접속해 리소스를 확인하는 방식이라 서버 20개 기준 2시간 이상 걸렸습니다.

이를 해결하기 위해 모니터링 스택 도입을 검토했습니다. 시각화와 알람 연동을 단일 도구로 처리할 수 있는 Grafana를 선택했고, 메트릭 수집은 Prometheus로 구성했습니다. Prometheus 기본 보존은 30일이었는데 1년치로 늘리려니 디스크 사용량이 크게 늘어, Thanos 등 별도 장기 저장 방식을 검토한 뒤 인프라 구성 변경 없이 가장 간단하게 도입할 수 있는 시계열 DB VictoriaMetrics로 전환해 1년치 메트릭을 안정적으로 보존할 수 있도록 했습니다.

40개 고객사 전체에 직접 구축하고 Google Chat 알람 연동까지 완료했습니다. 기존 KT Cloud Watch는 기본 자원 지표를 7일만 보존하고 알람도 메일로만 왔으며 40개 고객사를 한눈에 볼 통합 관제가 없었는데, 이를 통합 대시보드와 1년 장기 보존 체계로 전환했습니다. CMP 개발팀과 사전 협의한 Prometheus 연동을 통해, 기존에 구현돼 있으나 연동 환경이 없어 미활용되던 보고서 자동 생성 기능을 활성화했습니다. 이를 통해 2시간 이상 걸리던 수기 보고서 작업이 10분으로 줄었습니다.

**성과**
- 월간 보고서 작성 시간: 2시간 → 10분 (서버 20개 기준)
- 40개 고객사 통합 관제 대시보드 구축 (기존 KT Cloud Watch는 개별·통합 뷰 없음)
- 메트릭 보존 기간: 30일(Prometheus 기본) → 1년 (VictoriaMetrics 전환)

### WAF 유해 IP 차단 요청 반자동화  `[자동화/AI · 헤드라인]`
WAF에서 유해 의심 IP 이벤트가 발생하면 관리 업체에 차단 요청 메일을 보내야 했습니다. 기존에는 담당자가 메일을 일일이 확인하고 차단 요청 메일을 수동으로 작성해 발송하는 방식이었습니다.

*배경 — 왜 단순 자동화가 안 됐나.* 기관마다 규칙이 달랐습니다. 예를 들어 A 기관은 일본 IP는 차단하면 안 되고, 어떤 기관은 회신 시 특정 담당자를 참조(cc)에 넣어야 하는 등 기관별 예외 규칙이 있었습니다. WAF 관리 업체도 여러 곳이라 기관에 맞는 업체로 요청을 보내야 했습니다. "메일 읽고 차단 요청 보내기"가 단순 1:1이 아니었습니다.

**기여도 (팩트)**: 반복 작업이 번거로워 본인이 단독으로 파이프라인 구축 → 직접 운영으로 검증 후 팀에 전파.

*액션.* Gmail API와 MCP 서버를 로컬에 구성하고, 메일을 처리하는 Claude Code skill을 작성해 **기관별 예외 규칙을 지침에 인코딩**했습니다. "이벤트 처리해줘" 한 번이면 이벤트 메일을 파싱해 유해 IP 목록을 추리고, 기관에 맞는 업체로 보낼 차단 요청 회신을 작성하게 했습니다.

*시행착오 → 설계 결정.* 초기에는 AI가 담당 업체를 틀리게 분류하거나 메일 내용을 잘못 읽어 회신을 잘못 작성하는 경우가 있었습니다. 이 실패 모드를 관측하고, 완전 자동 발송 대신 **임시저장 → 사람 검토 → 발송**하는 승인 게이트를 두는 구조로 설계했습니다. 보안 사고 방지와 AI 오발송 방지를 동시에 확보한 선택이었습니다.

→ 반복적인 메일 확인·분류·작성 자동화 + 관측된 AI 실패 모드(오분류·오독)를 사람 승인 게이트로 차단 · 단독 구축 후 팀 전파

**플랜아이 백엔드 스코프 (팩트, 반드시 지킬 것):** 플랜아이(3개월)에서는 API 개발·도메인 로직 작성 같은 순수 백엔드 개발 업무가 없었다. 백엔드 이력서에서 플랜아이 대표 카드는 모니터링(인프라)이 아니라 **WAF/AI 자동화(로직·설계 요소가 있음)**로 잡는다. 플랜아이를 "백엔드 개발 경력"으로 부풀리지 말 것 — 리뷰어도 "DevOps/SRE로 읽힌다"고 지적함.

## 히스토리 서사

### RPMS - 자산계획관리 시스템

**프로젝트 소개**
국가정보자원관리원이 보유한 수십만 건의 IT 자산을 체계적으로 관리하기 위한 시스템입니다. 자산 현황이 항상 최신 상태여야 신규 신청이나 폐기·교체 결정을 정확하게 내릴 수 있어, 데이터 동기화가 핵심이었습니다.

**팀 구성·기여도 (팩트)**
- 개발 단계(2024.01~2025.06): PL 1, 선임 개발자 1, 본인, 신입 2 — 5인 팀.
- 운영 단계(2025.07~, 통합 운영유지보수): RPMS는 본인 단독 전담.
- **PL 공백 (팩트, 2026-07-29 확인)**: 통합 운영유지보수 사업으로 전환되면서 PL이 퇴사, 공식 직책 변경 없이(승진·발령 아님) RPMS 히스토리를 유일하게 아는 사람으로서 자연스럽게 그 역할을 이어받음. 실제로 맡은 일: 패치 방향 설정, 패치 일정 관리, 팀원 담당자 지정, 클라이언트 대상 시스템 사용법 교육·대응. 이력서엔 "실질적으로 전담"으로 표현 — "PL로 승진/임명됨"처럼 쓰지 말 것.

**자산 데이터 동기화 성능 개선 (2시간 → 10초)**  `[원인추적/성능 · 헤드라인]`
자산 현황이 최신 상태여야 신규 신청이나 폐기·교체 결정을 정확하게 내릴 수 있어, 동기화 기능은 RPMS의 핵심이었습니다.

이 동기화는 원래 연 2회 있는 설계 시즌에만 스케줄러로 도는 배치라, 다소 느려도 문제가 없었습니다. 그런데 인수인계 이후 기획이 "사용자가 필요할 때 버튼으로 즉시 실행"하는 방식으로 바뀌면서 문제가 드러났습니다. 배치를 직접 실행해보니 14만 건 처리에 2시간이 걸렸는데, 버튼을 누른 사용자가 결과가 나올 때까지 2시간을 기다려야 하는, 사실상 못 쓰는 구조였습니다. 스케줄러 기준으론 괜찮던 성능이 대화형(on-demand) 요구로 바뀌자 그대로 병목이 된 것입니다. 왜 이렇게 오래 걸리는지 코드를 뜯어보니 두 가지 병목이 있었습니다.

첫째, 기존 데이터와 비교하는 로직이 건마다 조회하는 방식이라 쿼리가 과도하게 많았습니다. 전체 데이터를 한 번에 조회해 HashMap으로 캐싱하고 인메모리에서 비교하는 방식으로 개선했습니다. 둘째, JPA IDENTITY 전략은 INSERT 시점에 DB에서 ID를 즉시 발급받아야 해 Bulk Insert가 불가능한 구조였습니다. JDBC Template 기반 Bulk Insert로 전환해 두 병목을 함께 해결했습니다.
→ 14만 건 처리 2시간 → 10초 (약 700배 = 720배, 감소율 99.86%)

**혼재된 쿼리 방식 통일로 유지보수성 개선**  `[유지보수성 · 헤드라인]`
JPA를 사용하면서도 단순 조회는 Data JPA, 복잡한 조건은 Criteria API, 쿼리 자체가 복잡해지면 Native Query를 쓰는 방식이 혼재해 있었습니다. 유지보수 시 같은 기능도 어떤 방식으로 구현됐는지 파악하는 것 자체가 부담이었습니다.

QueryDSL이라면 세 가지를 하나로 통일할 수 있다고 판단해 도입을 제안했습니다. Criteria API는 코드가 장황해 가독성이 나쁘고, Native Query는 문자열이라 오타가 런타임에 터지는 문제가 있었습니다. QueryDSL은 컴파일 단계에서 오류를 잡을 수 있고, JPA 영속성 컨텍스트를 그대로 활용할 수 있어 선택했습니다. 팀 내 회의적인 의견이 있어 자산 현황 모듈에 파일럿으로 먼저 적용한 뒤 직접 시연해 설득했고, 이후 지사 내 3개 프로젝트에 도입됐습니다.
→ 컴파일 단계에서 쿼리 오류 사전 감지 · 지사 내 3개 프로젝트로 쿼리 방식 통일 확산

- **주의 (2026-07-26)**: "Native 쿼리 70% 제거"는 삭제함 — 정확히 측정한 값이 아니고, 돌이켜보니 70%까지 줄었을지도 불확실. 정성적 결과(쿼리 방식 통일·컴파일 단계 오류 감지)만 사용.

**예산심사 감사 요구를 반영한 diff 기반 변경 이력 설계**  `[설계력/도메인 · 헤드라인]`
RPMS는 공공기관 예산심사 시스템이라 "누가 언제 무엇을 변경했는지" 추적 가능해야 하는 감사 요구사항이 있었습니다. 단순히 "수정 요청이 오면 이력을 남긴다"로 구현하면, 실제 값 변경이 없는 저장 요청에도 불필요한 이력이 과다 적재되어 감사 추적성을 오히려 저해하는 문제가 생깁니다.
서버·스토리지·네트워크 등 7종 자원 각각을 요청 값과 기존 데이터로 필드 단위(자원당 20여 개)로 비교해, 실제 변경이 있을 때만 이력을 적재하는 로직을 설계 단계부터 반영했습니다. 폼 입력값(문자열)과 엔티티 값(숫자·boolean) 간 타입 차이로 인한 오탐도 함께 처리했습니다.
→ 감사 대응에 필요한 변경 이력 추적을 만족시키면서, 심사자에게는 실제 변경분만 노출되는 신뢰도 있는 이력 제공

**사업유형별 검증 규칙 분리(Bean Validation Group)로 설계 오류 예방**  `[설계력/도메인 · 헤드라인]`
부분설계 등록 시 모든 자원 신청에 동일한 필수값 검증이 적용되는 구조였습니다. 하지만 실제 심사 규정은 사업유형(신규/증설/추가/노후/폐기)마다 요구하는 항목이 달랐습니다. 예를 들어 노후로 폐기 예정인 자산은 CPU·메모리 같은 상세 스펙을 입력할 필요가 없는데도 신규 도입과 동일한 필수값을 요구하면, 실무자가 어떤 값을 채워야 하는지 헷갈려 잘못된 설계로 이어질 수 있었습니다.
Bean Validation의 Validation Group을 사업유형별로 분리해, 사업유형 코드에 따라 런타임에 검증 규칙 자체가 다르게 적용되도록 설계했습니다. 폐기 대상 자원은 최소 식별 정보만 검증하고, 신규 도입 자원은 스펙 필드까지 엄격히 검증하는 식입니다.
→ 사업유형별로 다른 심사 규정을 코드 구조로 반영해, 실무자 입력 실수로 이어질 수 있는 설계 오류를 예방

**Self-Service API 전환으로 반복 운영 요청 대폭 절감**  `[효율/자동화 · 보조]`
고객이 자원을 신청하면 운영자가 직접 내부 시스템에서 자원을 생성해주는 매니지드 방식이었습니다. 티켓 등록·운영자 확인·장비 직접 설정 절차를 거쳐야 해 최소 1~2시간은 걸렸습니다. 반복 처리 요청이 체감상 월 50건 안팎으로 상당한 비중을 차지했고, 고객이 직접 자원을 제어할 수 없는 제한적인 CSP 구조였습니다.
CSP 인프라 특성상 장비 자체는 이미 멀티테넌트 기능을 갖추고 있었지만, 이를 고객에게 안전하게 직접 열어주려면 여러 벤더 장비를 안정적으로 오케스트레이션하는 문제를 먼저 해결해야 했습니다(관련 상세는 아래 Saga 패턴 항목 참고). 그래서 이 기능을 운영자 개입 없이 외부에 API로 직접 노출하는 별도 API 서버를 신규 개발했습니다. 고객이 직접 자원을 신청하고 즉시 처리되는 구조로 전환해 반복적인 수동 처리 업무를 없앴습니다.
- **정량 주의 (실측 아님, 2026-07-28 수정)**: "월 50건"은 로그 집계가 아니라 담당자 체감치라 배경(문제 상황) 서술엔 "안팎"으로 헤지해 유지하되, **전환 후 "한 자릿수 수준으로 감소" 같은 결과 쪽 파생 비교는 이력서 문구에서 삭제함** — 실제로 전환 후 건수를 추적 관찰한 적이 없어 이 비교치는 근거가 없었음. 결과는 숫자 대신 "반복적인 수동 처리 업무 해소"라는 구조적 서술로 대체. "최소 1~2시간"은 실측 로그가 아니라 티켓 워크플로우 절차(등록→확인→직접 설정)를 근거로 한 추정 — 면접에서 "어떻게 측정했나요?"엔 "직접 시간을 재본 건 아니고, 절차상 최소 그 정도는 걸릴 수밖에 없는 구조였다"고 답할 것. 면접에서 "체감 기준"임을 먼저 밝히면, 실측인 시간 측정치(2시간→10초, p95 17초→3초)까지 같이 의심받는 걸 막을 수 있음.
- **근거 (후속 대비)**: 이 체감치의 근거는 **배포·테스트하면서 운영 담당자와 자주 대화하고 그 업무를 옆에서 직접 관찰한 것**. 면접 "어떻게 아셨나요?"엔 "운영 담당자 업무를 옆에서 보고 자주 이야기하며 체감했다"로 답.
- **표기: "매니지드 방식" (이력서) / 실제 메커니즘: 티켓 워크플로우 (면접 답변용)**: 이력서에는 Self-Service의 반대 개념인 **"매니지드 방식"**(운영자가 대신 자원을 생성)으로 표기 — 매니지드↔셀프서비스 대비가 클라우드 맥락에서 깔끔. 실제 메커니즘은 **티켓 워크플로우**: 사용자가 자원 요청 티켓 작성(예: "SSD 500GB 증설 요청") → 스토리지 자산 담당자가 수동 증설 → 티켓 완료 처리. 면접에서 "구체적으로 어떤 방식이었나요?"엔 이 티켓 흐름(SSD 증설 예시)으로 답하면 서사가 탄탄해짐.
- **톤 주의 (기여 범위)**: "장비가 멀티테넌트 기능을 제공한다는 점에 착안해"라는 표현은 쓰지 말 것 — CSP 인프라 특성상 장비가 가상화·멀티테넌트를 지원하는 건 처음부터 주어진 전제였지, 본인이 발견한 인사이트가 아니었음. 실제 기여는 "그 기존 기능을 운영자 개입 없이 고객에게 직접 노출하는 API를 설계·구현한 것" — "~에 착안해"가 아니라 "장비가 이미 갖춘 기능을 운영자 없이 직접 노출하도록 설계"로 서술.
- **인과관계 확인 (팩트)**: "여러 벤더 장비의 안정적인 오케스트레이션 문제를 먼저 해결해야 했다"는 실제로 Self-Service 전환의 선행 과제였음(본인 확인) — 운영자가 수동으로 처리하던 시절엔 중간 실패를 사람이 즉시 발견해 대응할 수 있었지만, 고객이 직접 트리거하는 구조로 바꾸면 운영자 개입 없이도 partial failure를 안전하게 처리할 수 있어야 했기 때문. 반면 "테넌트 간 격리"는 이 카드의 선행 과제가 아니라 PPP 프로젝트 전체가 물리 할당 인프라에서 가상화 기반 클라우드로 전환하며 갖춰진 프로젝트 전반의 특성이므로, Self-Service 카드에 개별 성과처럼 넣지 말 것.

**멀티벤더 프로비저닝 오케스트레이션 구조 설계 (Saga 패턴)**  `[설계력/구조 · 헤드라인]`

*배경.* 고객마다 독립된 네트워크 환경(테넌트/Zone)을 만들려면 방화벽 계정 생성 → VS·인터페이스·라우트 설정 → ACI 초기화 → OpenStack 네트워크 생성까지 여러 벤더의 API를 순서대로 호출해야 했습니다. 이 벤더들은 서로 다른 외부 시스템이라 DB 트랜잭션은 물론 이를 자동화해주는 Spring @Transactional로도 묶을 수 없는 호출이었습니다. 문제는 이 흐름 전체가 하나의 서비스 메서드(setUpBasicResource, 131줄)에 몰려 있었고, 실패 시 롤백도 각자 try-catch로 작성돼 중복됐으며 실패 지점에 따라 처리 방식이 제각각이었다는 점입니다. 예를 들어 방화벽 계정 생성은 성공했는데 VS 생성 단계에서 실패하면, 이미 만들어진 계정이 존재한다는 이유로 재시도조차 불가능해지는 상황이 발생했습니다. 같은 문제는 포트포워딩(출발지·도착지·포트 객체를 순서대로 생성)처럼 여러 객체를 순서대로 만드는 다른 다단계 흐름에서도 반복됐습니다.

*액션.* 벤더 호출 순서를 조율하는 Integration 계층을 신설해 순수 DB 로직(도메인 서비스)과 벤더 어댑터를 분리하고, 엔티티 조립은 별도 Builder로 떼어내 오케스트레이션과 데이터 구성 책임을 나눴습니다. 이렇게 흐름을 한 곳에 모으고 나니 프로비저닝 단계(계정/VS/인터페이스/라우트/ACI/OpenStack/DB) 7곳마다 실패 지점을 명확히 구분할 수 있었고, 이를 바탕으로 단계별로 세분화된 예외 타입(총 11개)을 정의하는 구조를 제안하고 프레임워크를 구현했습니다. 공통 예외 클래스는 상속으로 재사용하고, 하위 예외마다 롤백에 필요한 컨텍스트만 추가하도록 했습니다. 도메인별 구체 롤백 로직(예: 계정 단계 실패는 계정만 삭제, OpenStack 단계 실패는 방화벽·ACI·네트워크를 역순으로 삭제)은 각 도메인을 가장 잘 아는 팀원들이 이 구조 위에서 직접 채워 넣었습니다.

*결과.* 실패 지점과 무관하게 이미 생성된 자원에 누수가 발생하지 않도록 구조적으로 보장했습니다. 벤더가 추가돼도 기존 흐름 변경 없이 새 예외 타입과 핸들러만 추가하면 되는 확장 가능한 구조를 확립했습니다.

- **면접 대비 (이력서 문구엔 안 넣음)**: 이 보장은 정확히는 "장비가 정상 응답한 실패"에 한정됨 — 네트워크 타임아웃처럼 장비가 아예 응답하지 않는 경우나 롤백 로직 자체의 실패는 이 보장 범위 밖. 이력서 문구는 간결함을 위해 이 단서를 뺐으니, 면접에서 "모든 실패를 다 커버하나요?"라고 물으면 이 한계를 정직하게 답할 것.

*배경.* Citrix 장비에서 백엔드 서버는 `{IP}_{PORT}`로 식별되는 하나의 Service 객체인데, 여러 개의 로드밸런서가 같은 백엔드를 공유해서 바인딩할 수 있다는 게 이 상품의 특성이었습니다. 문제는 여러 가상서버가 이 Service를 안전하게 공유하려면, 애플리케이션이 참조 상태를 직접 추적하고 있어야 했다는 것이었습니다(장비가 바인딩 관계 자체를 아는지와 무관하게, 참조 카운트 판단은 장비에 묻지 않고 저희 DB로 하기로 함). VM을 연결할 때 이미 등록된 Service가 있으면 중복 생성하면 안 됐고, 연결을 해제할 때는 다른 가상서버가 아직 그 Service를 쓰고 있는지 모른 채 삭제하면 엉뚱한 서비스의 백엔드가 끊길 위험이 있었습니다.

*액션.* 연결 시에는 장비에 먼저 Service가 존재하는지 조회해서, 있으면 타입을 확인하고 재사용하고 없으면 새로 생성하도록 처리했습니다. 해제 시에는 DB에서 같은 IP·Port를 참조하는 다른 활성 바인딩이 있는지 쿼리로 확인해서, 없을 때만 실제 장비에서 Service를 삭제하도록 만들어 참조 카운팅을 구현했습니다.

*결과.* 여러 가상서버가 백엔드를 안전하게 공유할 수 있는 구조를 확보했습니다. 애플리케이션 레벨에서 참조 상태를 직접 관리해 중복 생성과 사용 중인 자원의 조기 삭제를 방지했습니다.

- **팩트 출처**: 소스코드를 직접 보고 확인한 내용(2026-07-27).
- **톤 주의 (과장 정정)**: "장비 자체엔 참조 카운트 개념이 없다"는 검증 안 된 과장 — 장비가 바인딩 관계를 아는지는 불명확하고, 실제로는 "장비에 묻지 않고 참조 상태를 우리 DB/애플리케이션에서 직접 판단하기로 한 것"이 정확한 표현. 마찬가지로 "상태를 갖지 않는 벤더 API"도 부정확 — Service 객체 자체는 장비에 저장되는 상태이므로, 없는 건 "참조 카운트라는 상태"뿐.

**벤더 장비 스펙 불일치를 통합 테스트로 사전 검증**  `[품질/검증 · 헤드라인]`

*배경.* PPP Cloud의 네트워크 상품은 방화벽·로드밸런서 등 테넌트의 최전방 네트워크 장비를 전부 다루는 구조라, 이 설정 하나가 실패하면 테넌트 네트워크 자체가 구성되지 않아 방금 만든 VM에도 도달할 수 없었습니다. 그런데 벤더 장비마다 전달받은 스펙 문서와 실제 동작이 달랐습니다. 안랩 방화벽은 문서의 API 설정 필드명에 오타가 있었고, Citrix는 쿼리 파라미터를 독자적인 방식으로 인코딩해야 했습니다(이 IP_PORT 관련 사건이 위 "로드밸런서 참조 관리" 카드의 설계 동기이기도 함).

*액션.* 벤더 장비 연동을 검증하는 테스트 문화는 없었지만, 연동 기능을 개발할 때마다 이런 문제로 고치고 다시 배포하는 과정이 반복되자 사전 검증이 필요하다고 판단했습니다. `@SpringBootTest` + `@ActiveProfiles("test")` 구조로, `@MockBean`이나 WireMock/MockWebServer 같은 스텁 없이 실제 Spring Bean(`TrusGuardVsService`, `citrixAdminWebClient` 등)을 그대로 주입받아 실제 스테이징 장비(TrusGuard·Citrix L4·ACI·L3 스위치)를 직접 호출하도록 설계했습니다. `@BeforeEach`에서 실제 계정을 생성하고 `@AfterEach`에서 삭제하는 등, 각 테스트가 장비 위의 상태를 스스로 만들고 정리하도록 했습니다.

*결과.* 벤더별 스펙 불일치(필드명 오타, 독자 인코딩 등)를 배포 전에 잡아낼 수 있었고, 최전방 네트워크 설정 실패가 테넌트 전체 연결 장애로 번지는 상황을 사전에 막았습니다.

- **팩트 출처**: 본인이 실제 코드를 확인한 내용(2026-07-28).
- **DB 레이어 주의**: DB는 H2 인메모리(테스트 격리용)이지 실제 MySQL이 아니므로 "완전히 프로덕션과 동일한 환경"이라고 쓰면 과장. 실장비 대상인 건 벤더 연동 레이어뿐.

**멀티테넌트 네트워크 상품 데이터 모델 설계**  `[설계력/구조 · 보조 · 이력서·경력기술서 제외]`

**반영 결정 (2026-07-28, 경력기술서에서도 제외로 수정)**: 배경에 구체적 실패/충돌 사건이 없고 결과도 정성적 서술뿐이라, Self-Service·Saga·로드밸런서 참조관리 3개 대비 도메인 문제해결이 약함. resume.ts의 `resumeContent`(이력서 본문)와 `achievements`(경력기술서 아코디언) 양쪽 모두에서 제외. portfolio.ts에는 유지 — 면접·포트폴리오용 소재로만 보관.

*배경.* 고객(테넌트)마다 독립된 네트워크 환경을 제공해야 했습니다. 방화벽·LB 등 각 벤더 장비가 실시간 상태 조회 API를 자체 제공해, DB가 장비 전체 상태를 복제할 필요 없이 테넌트-자원 매핑·오케스트레이션에 필요한 최소 서비스 데이터만 저장하면 됐습니다. 그래서 테넌트별 스키마 분리를 할 만큼 데이터 볼륨·복잡도가 크지 않다고 판단, 단일 스키마 + FK 그래프 논리 격리를 택했습니다. 다만 상품 도메인마다 격리 특성이 달라 방화벽/LB 모델링은 다르게 설계했습니다.

*액션.*
- **방화벽(엄격한 그래프형)**: Zone(테넌트) 1:N FireWallVs 1:N FireWallInterface 1:N FireWallPublicIp 1:N FireWallPortForwarding. zone_idx 컬럼은 테넌트 경계의 루트인 FireWallVs에만 두고, 하위 엔티티는 상위로 조인해 올라가야 테넌트를 식별하도록 정규화.
- **LB(비정규화형)**: LoadbalancerEntity에 zone_idx FK와 함께 lb_partition 컬럼(값=rootIam)을 나란히 저장. DB 레벨 테넌트 식별자(zone_idx)와 장비 레벨 테넌트 식별자(Citrix의 Partition 이름)를 동시에 보관해, DB 조회와 장비 API 호출에 각각 맞는 키를 즉시 쓸 수 있게 함.
- **이중 격리**: DB는 FK 기반 논리 격리(공유 스키마), 물리 장비는 테넌트별 격리 — TrusGuard는 테넌트별 VS(Virtual System), Citrix는 테넌트별 Partition을 만들어 하드웨어에서 트래픽 자체를 분리. "DB 컬럼 논리 격리 + 장비 파티션 물리 격리"의 2단 구조.

*결과.* 도메인마다 격리 요구가 다른 멀티테넌트 상품을 단일 스키마 위에서 관리하면서, DB와 장비 양쪽 테넌트 키를 함께 다뤄 조회·프로비저닝 경로를 단순화.

**톤 주의 (반드시 지킬 것):** 이 테넌트 격리는 "데이터 모델상 구분"이지 보안/인가가 아니다. 이 API 서버 자체엔 인증이 없었고(Spring Security 비활성), "호출자가 자기 zone_idx만 조회하도록 강제"하는 인가는 이 서비스 책임이 아니라 상위 CMP가 인증된 rootIam/zoneId를 넘겨준다는 전제에 의존한다. → 멀티테넌트 격리를 "보안 설계"로 포장 금지 ([[fact_no_auth_in_ppp]]). 면접에서 "인가는 어디서?"에 대비: "이 서비스는 CMP가 넘긴 zoneId를 신뢰하는 내부 API였고, 인가 경계는 CMP에 있었다"고 정직하게 답할 것.

**L4 로드밸런서 상품 — 벤더 장비 추상화**  `[설계력·보조]`
Citrix(LB)·TrusGuard(방화벽) 등 벤더 장비의 기능을 온전히 이해한 뒤, 이를 클라우드 네트워크 상품 기능으로 추상화해 API로 제공하는 어댑터 개발이 L4에서 가장 까다로운 부분이었습니다. 장비별 개념(Partition, VS 등)을 상품 도메인 모델에 대응시키는 매핑이 핵심이었습니다.

## 히스토리 서사

> **에이직스 전체 축: `[보조]`** — 가장 오래된 SI 경력(레거시 스택). 백엔드 이력서 헤드라인이 아니라 "기본기·비효율 개선 전례"의 보조 근거로만 사용. 단 **Soft Reservation은 예외로 `[설계력·보조]`** 승격(동시성 설계 사례라 앵커에 부합). Tiles는 `[팀기여·보조]`, Jenkins/DB이관은 `[인프라·보조]`.

### Tiles 프레임워크 도입
한전 프로젝트에서 JSP 페이지마다 헤더·푸터·네비게이션을 반복 복붙하는 구조로 개발이 이루어지고 있었습니다. 페이지 수가 늘어날수록 레이아웃을 수정할 때 전 페이지를 일일이 손봐야 했고, 신규 페이지 개발 리드타임도 2일이 걸렸습니다.

레이아웃 템플릿화가 가능한 Tiles 프레임워크 도입을 팀에 직접 제안하고 적용했습니다. 결과적으로 중복 코드가 65%에서 10%로 줄었고, 페이지 개발 리드타임이 2일에서 0.5일로 단축됐습니다.

### Jenkins 배포 파이프라인 구성
수동 배포 방식으로 운영하다 보니 휴먼에러가 잦았고, 배포 주기가 7일로 길어 긴급 패치 대응이 어려웠습니다. SI 폐쇄망·온프레미스 환경 특성상 관리형 SaaS CI는 사용할 수 없었기 때문에, 자체 구축이 가능한 Jenkins를 선택해 파이프라인을 직접 구성했습니다. 이후 배포 빈도가 7일에서 1일로 줄었습니다.

### 충남도청 SMS 서비스 DB 이관 및 쿼리 최적화
노후 장비를 교체하면서 OS 설치, 1,000만 건 데이터 마이그레이션, 장비 납품까지 전 과정을 담당했습니다. 데이터 무결성을 100% 유지하며 이관을 완료했고, 이관 후 다운타임도 발생하지 않았습니다.

이관 과정에서 성능 문제도 발견했습니다. 헤더에서 전체 SMS 카운트 집계 쿼리가 페이지 이동마다 자동 실행되어 로딩이 지연되고 있었습니다. 상시 표시가 불필요한 집계라는 점을 파악해 버튼 클릭 시에만 조회하는 방식으로 변경했고, p95가 5초에서 0.9초로 개선됐습니다.

### FastAPI 크롤링 서버 구축
한전 프로젝트에서 앱과 웹에서 동일한 PDF 보고서를 생성해야 했습니다. jsPDF는 브라우저 렌더링 환경이 필요해 Spring에서 직접 실행할 수 없는 구조였습니다. 앱 개발팀과 논의하다 크롤링 서버를 별도로 두는 아이디어가 나왔고, 빠른 구현이 가능한 FastAPI를 선택해 직접 구축했습니다.

### 동구청 과학행사 신청 플랫폼 — Soft Reservation  `[설계력·보조]`
동시 신청이 몰릴 경우 한 사람이 중복 신청할 수 있는 가능성이 있었습니다. Redis 분산락은 별도 인프라 구성이 필요했고, DB 비관적 락은 소규모 행사 트래픽에 과도한 설계였습니다. 별도 인프라 없이 DB에 임시 예약 상태를 두고 관리하는 Soft Reservation 방식을 설계해, DB 제약(UNIQUE) 기반으로 중복 신청을 막는 구조를 적용했습니다.
사용자가 예약 페이지에 진입하면 해당 자리를 선점하는 API를 호출해 임시 점유 상태로 두는 방식이었습니다.
- **불확실 메모**: 임시 상태의 만료 처리·확정 전이 세부(타임아웃 자동 해제 여부 등)는 기억이 흐릿함("상태값을 임시로 둔 것 같다" 수준). 면접에서 깊이 물으면 단정하지 말고 "임시 점유 상태 컬럼으로 관리했고 확정 시 전이시키는 방식이었던 것으로 기억한다"고 범위를 정직하게 답할 것.

## 자기소개 (본인 언어, 2026-07 재편 — 안정성·유지보수성 정체성)
> **표면이 아니라 근본 원인을 고치는 백엔드 개발자 노성웅입니다.**
>
> 기술을 목적이 아니라 문제 해결의 도구로 보고, 성능 병목을 끝까지 추적해 해결하며, 만든 사람이 아니어도 읽고 유지보수하기 쉬운 코드를 만드는 데 강점이 있습니다.
>
> **Spring Boot/Java 기반으로 공공 클라우드 환경에서 수십만 건 규모의 자산 데이터**를 다루며, 성능 개선과 다단계 트랜잭션 구조 설계, 쿼리 방식 표준화를 해왔습니다.
>
> 당장 돌아가게 하기보다, 원인까지 해결해서 오래 안정적으로 유지되는 시스템을 만들려고 합니다.

- **구조**: 정체성 선언 → 일하는 방식/강점 → 구체 경력(스택·규모·성과) → 추구 가치. 4문단.
- **정체성 축**: 시스템 안정성 + 유지보수성. 안정성은 성능 병목 해결·트랜잭션 구조 설계로, 유지보수성은 읽기 쉬운 코드·쿼리 표준화로 뒷받침(원천 데이터 헤드라인 카드와 정합).
- **가드레일**: 안정성을 모니터링·장애 감지·운영으로 풀지 말 것 — SRE 정체성으로 미끄러짐(리뷰어 #1 지적). 백엔드 행위(성능·코드 구조·트랜잭션 설계)로만 풀 것.
- **스택 정직성**: 이 자기소개 문장에서는 "Spring Boot/Java"로 표기(본인 지시로 JPA는 문구에서 뺌 — JPA 자체가 스택에서 빠진 건 아님). Kotlin은 실무 없음이라 절대 추가 금지.
- **이전 버전(교체됨)**: "문제의 표면이 아니라 코드·실행계획까지…" 3줄(당근 지원 때 확정). 성능+팀 중심이라 유지보수성·안정성 정체성이 약해 교체.

## 낯선 도메인에 빠르게 적응한 전례
에이직스에서는 SI 풀스택(eGovFramework, MyBatis, JSP)만 다뤘고 클라우드는 실무로 접한 적이 없었다. 오케스트로에 합류하면서 프라이빗 클라우드·CSP라는 낯선 도메인에 처음 진입했지만, 빠르게 익혀 RPMS 성능 개선(2시간 → 10초), PPP Cloud 신규 네트워크 상품 개발까지 주도했다.

- **활용처**: 지원 회사의 도메인 경험이 없을 때(로봇, 핀테크, 의료 등) "도메인은 낯설어도 빠르게 적응해 성과를 낸 전례가 있다"는 근거로 사용. 기술 스택 도입 사례(FastAPI·QueryDSL·VictoriaMetrics)보다 도메인 무경험 방어에 더 직접적으로 꽂힘.
- **실사용 이력**: 현대오토에버 RX기술팀(로봇 관제) 지원 사전질문에 사용.
